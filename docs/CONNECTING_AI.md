# Как подключить протокол к разным ИИ

Это руководство по подключению, а не новые правила протокола. Проверено по коду проекта и официальной документации клиентов 30 сентября 2026 года. Доступ определяется приложением и выданными инструментами: одна и та же модель в браузерном чате и в локальном агенте имеет разные возможности.

## Что именно подключается

**Правила работы:** `PROTOCOL.md`. ИИ должен прочитать текст и применять требования к текущей задаче. Наличие файла на диске ещё не означает, что текст попал в контекст модели.

**Память проекта:** `memory/*.md` содержит состояние, решения, вопросы, ошибки и калибровку. Версионные записи атласа хранятся отдельно в `data/memory.sqlite3`. Изменение записи в базе не переписывает Markdown-файлы; изменение Markdown требует нового импорта в атласе.

**Проверки:** `check_answer.py` ищет признаки нарушений в черновике; API проверяет ссылки и версии записей. Проверка ссылок подтверждает существование цитаты, но не правильность вывода из неё.

**Регулятор C/D:** C ограничивает нагрузку одного шага, D — самостоятельность ИИ при выборе решений. Сейчас программа моделирует изменения этих параметров на стенде. Автоматического запрета действий внешнего агента по C/D нет. Для такого запрета нужен контроль вызовов инструментов в приложении агента.

## Какой части протокола доступны разные клиенты

| Где работает ИИ | Как передать правила | Какая память доступна | Что можно проверять и исполнять |
|---|---|---|---|
| Браузерный чат без инструментов доступа к проекту | Вставить текст или приложить файлы, явно попросить их прочитать | Только переданный снимок; обновления папки нужно передавать заново | ИИ следует тексту; проверки запускает человек. Сам чат не записывает локальные файлы |
| Чат с подключением файлов или MCP | Передать инструкцию и дать инструмент чтения | То, что возвращает подключённый инструмент в пределах его прав | Чтение, а при разрешённом инструменте — запись. Контроль действий зависит от приложения |
| Локальный Codex | Короткий указатель в `AGENTS.md`, затем чтение `PROTOCOL.md` | Файлы в доступной рабочей области; локальный API через инструмент агента | Запуск скрипта, чтение и разрешённая запись; исполнение C/D требует отдельного контроля |
| Claude Code | Короткий указатель в `CLAUDE.md`, затем чтение файлов | Файлы в разрешённых каталогах; инструменты MCP при настройке | Запуск проверок и запись в пределах разрешений клиента |
| Gemini CLI | Короткий указатель в `GEMINI.md`, затем чтение файлов | Файлы, доступные клиенту; подключённые инструменты | Проверки и запись при наличии разрешённых инструментов |
| Собственный агент через API модели | Программа читает протокол и передаёт инструкции в запросе | Программа собирает актуальные записи и передаёт их модели либо предоставляет инструменты чтения | Программа запускает проверки, сохраняет результаты и может ограничивать действия |
| Локальная модель в собственном приложении | Передать протокол в инструкции и контекст | Только файлы и инструменты, предоставленные приложением | Возможности зависят от приложения; установка модели сама по себе не подключает память |

Чат с загруженными файлами получает копию материалов на момент загрузки. Для живого доступа к общей папке нужен инструмент, который действительно читает эту папку. Возможности подключения в конкретном сервисе нужно проверять для вашего клиента и аккаунта.

## Начать без нового API: локальные агенты

1. Выберите одну постоянную папку протокола. Для этого проекта это папка `protocol_AI`, где лежат `PROTOCOL.md` и `memory/`.
2. Откройте её как рабочую область агента либо разрешите чтение этого каталога из рабочей области другого проекта.
3. В инструкции клиента добавьте указатель на постоянный абсолютный путь. Для Codex используется `AGENTS.md`, для Claude Code — `CLAUDE.md`, для Gemini CLI — `GEMINI.md`. Сохраните существующие инструкции клиента и добавьте указатель к ним.
4. Попросите агента прочитать протокол и нужные файлы памяти. Путь в инструкции помогает найти файл, но доступ к файлу всё равно должен быть разрешён средой.
5. Начните с общего чтения. Назначьте один процесс или человека, который сохраняет принятые изменения памяти. Для одновременной записи используйте сервис версионной памяти.

Пример инструкции для файла клиента. Замените `<абсолютный путь к protocol_AI>` настоящим путём; это шаблон, а не готовая настройка:

```text
Папка протокола: <абсолютный путь к protocol_AI>.
В начале задачи прочитай PROTOCOL.md из этой папки,
затем memory/STATE.md и memory/DECISIONS.md.
Прочитай другие файлы memory/, относящиеся к задаче.
Сообщи, какие файлы удалось прочитать и какие недоступны.
Применяй протокол в рамках правил и разрешений своего клиента.
Не считай гипотезы и предложения принятыми решениями.
Перед продолжением после смены сессии перечитай состояние.
При общем режиме чтения предложи изменения памяти человеку.
Если включена запись через сервис, передавай изменения с ожидаемой версией.
```

Такой указатель нужно добавить в каждый проект или в общую настройку клиента с подходящей областью действия. Не требуется копировать весь протокол в каждый проект. Git-копии и синхронизированные папки остаются отдельными экземплярами: они могут расходиться до синхронизации.

## Браузерный чат: подключение вручную

Приложите `PROTOCOL.md`, `memory/STATE.md`, `memory/DECISIONS.md` и документы по текущей задаче. Напишите: «Прочитай приложенный протокол, назови полученные документы и примени его к этой задаче. Если данных не хватает, укажи, каких именно».

После работы попросите подготовить предложения для обновления памяти с причинами и источниками. Сохраните их в общей папке после проверки. При следующей сессии передайте актуальные файлы снова. Если клиент умеет подключать сервисы, настройка живого доступа выполняется через поддерживаемый им инструмент; загрузка файла этот доступ не заменяет.

## Собственный агент через API модели

API модели получает запросы на генерацию ответа. API протокола предоставляет ваши правила, память и проверки. Это две разные функции: ключ OpenAI, Groq или другого сервиса не даёт модели доступ к вашему диску.

Перед каждым новым этапом программа агента получает актуальную сборку кратких правил через `GET /api/runtime-rules` и собирает материалы задачи. Состав групп выбирается явно, постоянное ядро не исключается. Правила передаются в поле инструкций API, а источники и память — как материалы. Запросы и проверки сохраняются; новые выводы не принимаются автоматически. Подробности и границы — [руководство по сборке](RUNTIME_RULES.md). После смены сессии программа заново восстанавливает необходимые правила и память.

В лаборатории проекта уже реализованы вызовы OpenAI, Groq и Cerebras. Это подключения для опытов с памятью; они не означают, что произвольные ваши агенты уже используют протокол. Чтобы агент работал с общей памятью, его программа должна вызывать локальный сервис или читать файлы и передавать их модели.

## Что уже предоставляет локальный API проекта

Запуск из папки проекта:

```powershell
py -3 -m protocol_atlas.server
```

Адрес сервиса: `http://127.0.0.1:8765`. Он доступен на этом компьютере. Для сервера другого компьютера, контейнера или облачного чата `127.0.0.1` указывает на их собственную среду, а не на ваш компьютер.

| Действие | Существующий маршрут | Что возвращает или изменяет |
|---|---|---|
| Прочитать протокол и исходную память | `GET /api/catalog` | Полный текст зарегистрированных источников, разделы и SHA-256 |
| Прочитать это руководство | `GET /api/connections` | Текст руководства, разбитый на блоки |
| Предпросмотр правки документа | `POST /api/source/preview` | Разбирает Markdown из полей `path`, `text`, не меняя файл |
| Сохранить исходный документ | `POST /api/source/save` | Записывает Markdown с проверкой `expected_sha256`, сохраняет прежний текст в `data/source-history/` |
| Получить список записей | `GET /api/memory` | Версионные записи и состояние оснований |
| Прочитать запись | `GET /api/memory/<id>` | Текущая версия; параметр `revision` выбирает сохранённую версию |
| Импортировать Markdown-источники | `POST /api/memory/import` | Снимки файлов и записи; импорт не означает принятия содержания |
| Собрать контекст | `POST /api/memory/assemble` | Выбранные записи и их основания; поля запроса `ids`, `goal`, `budget` |
| Сохранить запись | `POST /api/memory/save` | Новая версия; для правки существующей записи нужен `expected_revision` |
| Проверить ссылки ответа | `POST /api/memory/check-response` | Проверка ответа относительно точной сборки контекста |
| Проверить черновик | `POST /api/check-answer` | Эвристические замечания к тексту |
| Испытать переходы C/D | `POST /api/regulator` | Результат симуляции; внешние инструменты агента не блокируются |

POST-запросы отправляются с `Content-Type: application/json`. Точные поля записи определены в `protocol_atlas/memory.py`, проверки ответа — в `protocol_atlas/context.py`. Результат сборки может сообщать о пропущенных или устаревших основаниях и превышении бюджета: агент должен обработать эту диагностику перед продолжением.

Существующий API рассчитан на локальное приложение. У него нет индивидуальных учётных записей агентов, прав по ролям и удалённой аутентификации. Подключать локальные программы можно через этот сервис; публиковать его в сеть без отдельного слоя доступа не следует.

## Нужен ли новый API и зачем MCP

**Для нескольких локальных агентов, читающих одни правила, достаточно общей папки и инструкций клиентов.** Новый API для такого чтения не обязателен.

**Для одновременной записи общей памяти полезен единый сервис.** В этом проекте уже есть основа: SQLite, неизменяемые версии и проверка ожидаемой версии. Если два агента прочли версию 4 и первый сохранил версию 5, попытка второго изменить запись с `expected_revision: 4` отклоняется. Второй должен перечитать запись и согласовать изменение. Обычная запись в один Markdown-файл такой защиты не даёт.

**Для подключения клиентов через MCP нужен адаптер.** MCP — стандарт, через который приложение ИИ вызывает инструменты сервиса. Это позволит предоставить операции чтения протокола, сборки контекста, предложения записи и проверки ответа. MCP не заставляет ИИ соблюдать правила; приложение всё равно должно передавать инструкции и определять права инструментов. Сейчас MCP-сервер этого проекта не реализован; HTTP-маршруты сами по себе не являются MCP-сервером.

Рекомендуемая схема для ваших агентов: одна папка с протоколом и источниками → один сервис версионной памяти → прямой HTTP-доступ для собственных программ и MCP-адаптер для совместимых клиентов. Все записи проходят через один сервис; агенты не редактируют SQLite напрямую. Принятие нового правила остаётся отдельным решением человека.

Для удалённых клиентов следующий этап — адрес доступного им сервиса, аутентификация, разрешения на чтение и запись и журнал автора изменения. Для автоматического исполнения C/D нужен ещё слой, который проверяет допустимость операции перед вызовом инструмента. Эти части предлагаются как развитие; сейчас их нет.

## Как убедиться, что подключение работает

В конце подключения локального агента интерфейс выдаёт «Первое сообщение» отдельно от инструкции для файла клиента. Описание из начальной настройки подставляется автоматически; материалы и первый шаг можно уточнить обычным текстом. Скопируйте сообщение или скачайте FIRST_MESSAGE.md, откройте рабочий проект в Codex и отправьте его в новый чат. Дальнейшая разработка идёт в этом чате: агент читает правила, выполняет небольшой шаг, проверяет результат и обновляет память проекта. Человек проверяет отчёт и принимает результат либо просит доработку. Изменения самого протокола обсуждаются отдельно, когда обнаружено ограничение правил.

1. Попросите ИИ прочитать конкретный раздел `PROTOCOL.md`, назвать его заголовок и привести короткую точную цитату. Сверьте цитату с файлом или каталогом.
2. Добавьте в тестовый файл памяти уникальную метку и попросите ИИ перечитать файл. При передаче вложений загрузите новую копию. Ответ со старой меткой показывает, что используется прежний снимок.
3. Попросите назвать принятые решения и открытые вопросы отдельно, с указанием документов. Проверьте, что гипотеза не стала принятым решением.
4. Если включена запись через сервис, проверьте её на отдельной тестовой записи: новая версия должна сохранять старую, а правка с устаревшей ожидаемой версией — отклоняться.
5. Начните новую сессию и повторите чтение состояния. Это проверяет восстановление доступа, но ещё не доказывает соблюдение всех правил ИИ.
