# Работа в своём проекте

Теперь основное место работы — чат выбранного ИИ. Атлас выдаёт одно стартовое сообщение и остаётся необязательным местом просмотра правил. Тип, объём, сложность, этапы и критерии составляет агент из свободного описания. Собственный API модели для стартового окна не требуется; прежние инструменты атласа по-прежнему могут использовать своё подключение в «Мой ИИ».

## Подключение

В атласе откройте «Начать работу», опишите цель, выберите среду и скопируйте готовое сообщение в чат открытого рабочего проекта. Путь к этому установщику подставляется автоматически; папка нового проекта определяется по текущей рабочей папке агента.

Альтернатива — «Скачать подключение»: распаковать `protocol-runtime.zip` в рабочий проект и один раз выполнить:

```powershell
py -3 install_protocol.py install --client codex --project .
```

Для других клиентов заменить `codex` на `claude`, `gemini`, `generic`, `api` или `files`. Существующие AGENTS.md, CLAUDE.md или GEMINI.md сохраняются, блок протокола дополняется отдельно. У Codex подготовлены проектные MCP, native skill и hooks. Для hooks клиенту нужно однократное доверие установленному коду; установка сама не меняет глобальные разрешения или сохранённое доверие. После переноса проекта на другую машину повторная установка обновляет пути инструментов.

Состояние атласа, история чужого проекта и API-ключи в комплект не попадают. Нужен Python 3.10 или новее; дополнительных Python-пакетов нет. `.protocol/project.sqlite3` — собственное состояние рабочего проекта. `.protocol/state.json` и `STATE.md` — восстанавливаемые представления, их не нужно заполнять вручную.

## Дальнейшая работа

Пишите цель и замечания обычными сообщениями в том же чате. Skill требует, чтобы агент сам записывал план, критерии, выполненные проверки и результат. Содержательная новая цель создаёт задачу; короткая реплика или запрос статуса не требуют новой схемы этапов.

Проверенный промежуточный результат открывает зависимый этап автоматически. Выбор с `gate=human` ожидает принятия человеком. `verified` означает пройденные актуальные критерии, `accepted` — отдельно переданный отзыв человека. Сам движок не удостоверяет личность автора сообщения: клиент отвечает за точную передачу реальной человеческой реплики.

Каждая проверка связана с контрольными суммами файлов. Изменение файла или проверенной версии входного этапа отправляет связанные результаты на пересмотр. Ошибка команды, таймаут, пропавший файл и изменение файла во время проверки не превращаются в успешное завершение. Повтор запроса с тем же идентификатором не дублирует действие в пределах сохранённой истории; старый запрос после её сокращения отклоняется по версии.

Замечание к оформлению адресуется этапу оформления; изменение данных затрагивает расчёты и визуализацию. Агент сохраняет точный текст отзыва. Накопленный опыт применяется к тому же клиенту, известной модели и типу этапа; ошибка или поправка возвращает рекомендацию уменьшить объём и отдельно проверить причину. Это наблюдаемые факты и рекомендации, а не измеренные универсальные числовые C/D. Неизвестная модель и один успех не повышают пределы.

## Способы обращения к одному ядру

| Способ | Что работает | Что остаётся на стороне клиента |
| --- | --- | --- |
| Codex | AGENTS.md, skill, локальный CLI, подготовленные MCP и lifecycle hooks | Доверие hooks, разрешения на инструменты, применение skill агентом |
| Claude Code | CLAUDE.md и тот же локальный инструмент | Чтение инструкции, исполнение цикла; native hooks этого клиента ещё не реализованы |
| Gemini CLI | GEMINI.md и тот же локальный инструмент | Чтение инструкции, исполнение цикла; native hooks этого клиента ещё не реализованы |
| Другой агент | AGENTS.md и JSON CLI | Доступ к файлам и командам |
| API | Локальный HTTP и JSON-операции | Собственная модель, её вызовы и инструменты разработки |
| MCP | stdio JSON-RPC, discoverable tools с входными схемами | Регистрация сервера и разрешения в выбранном клиенте |
| Чат с файлами | Пакет контекста и проверяемый импорт продолжения | Передача пакета туда и обратно; локальные командные проверки выполняет агент или программный клиент |

CLI:

```powershell
py -3 .protocol/engine/runner.py context --project .
py -3 .protocol/engine/runner.py start --project . --input request.json
py -3 .protocol/engine/runner.py mcp --project .
py -3 .protocol/engine/runner.py serve --project . --port 8770
```

`request.json` создаёт агент или программа, не пользователь. Изменяющие операции получают `expected_revision`; конфликт не перезаписывает замечание другого клиента. Все способы сохраняют одинаковый смысл статусов.

HTTP доступен на `127.0.0.1`, чтение — `/protocol/status`, `/context`, `/export`, `/events`; запись — POST `/protocol/<action>` с JSON. Host и Origin проверяются; записи с чужого сайта отклоняются. Python-процесс выполняет проверочную команду с собственными разрешениями: рабочая папка команды не является файловой песочницей. Клиент должен применять обычную политику разрешений к своим инструментам.

Для продолжения файлами экспорт содержит проект, базовую версию, состояние, контекст и `operations`. Добавить операции и пересчитать контрольную сумму может ИИ или программный клиент. Команды из импортированного пакета автоматически не исполняются. Снимок из другой рабочей папки не заменяет состояние существующего проекта; импортированные командные свидетельства требуют локального подтверждения. Контракт полей лежит в установленном skill: `references/contract.md`.

Пакет включает также сам skill, контракт и правила для нового чата. Текстовому ИИ достаточно вернуть заполненный `reply_template`: пересчитывать контрольную сумму всего исходного пакета не нужно. Импорт такого ответа по-прежнему проверяет проект, базовую версию и допустимые операции; человек переносит файл, не заполняя поля постановки.

## Стенд и хранение

При запущенном `serve` адрес `http://127.0.0.1:8770` показывает цели, этапы, тип, объём, сложность, критерии, реальные исходы команд, происхождение свидетельств, версии артефактов, замечания и рекомендации по нагрузке. «Состояние рабочего проекта» в атласе показывает папку, из которой запущен атлас; оно не сканирует соседние проекты. Чтобы увидеть внешнее приложение, его агент запускает `serve` именно в том проекте. Открывать панель для выполнения каждого этапа не требуется.

Наличие настройки подключения и фактически наблюдённые события среды показываются отдельно. Hooks хранят служебные идентификаторы и контрольные суммы, без текста prompt, tool_input или tool_response. Полный внутренний запрос внешнего клиента и расход модели из этих событий не восстанавливаются.

По умолчанию: последние 2000 событий среды, последние 2000 изменений состояния, текст команд только при ошибке (не более 12000 символов). Можно отключить историю событий среды, выбрать глубину истории изменений и сохранять весь вывод команд либо только итог и контрольную сумму. Удаление старых изменений не удаляет текущие задачи, результаты, замечания или версии артефактов. SQLite повторно использует освободившиеся страницы; физический размер файла не обязан уменьшиться сразу. Артефакты остаются обычными файлами проекта и не копируются в каждый журнал.

## Что проверено

36 проверок нового ядра покрывают переходы, зависимости, адресные изменения плана, замечания, ошибки, таймаут, версии, повторные запросы, восстановление представлений, импорт, настройки хранения, изоляцию опыта, установку вне атласа и совместимость интерфейсов. Проверен настоящий stdio-процесс MCP вне исходной папки. Полный набор проверок приложения включает также прежние механизмы.

Обычный контекст и ответы на операции включают активную задачу, а не все прошлые свидетельства. Артефакты неактивных задач не перечитываются на каждом ходе; полный `status` и экспорт проверяют все задачи. Область проверки явно возвращается в `artifact_validation_scope`. Входные схемы MCP содержат только поля конкретной операции.

`scripts/run_runtime_demo.py` воспроизводит «тестовые данные → статистика → SVG» через CLI, HTTP, MCP и пакет файлов. Он завершается в `awaiting_review`, не записывая принятия человека. Данные синтетические; API реальной конференции и API ИИ этим прогоном не проверены. Документы учебного сценария и созданное в другом проекте изображение не выдаются за подтверждённый результат.

Два пробных вызова установленного Codex CLI отклонены политикой его среды при чтении через PowerShell, несмотря на запрошенный `workspace-write`. Изменения глобальных разрешений не выполнялись. Тестовые отчёты сохранены в `build/runtime-smoke-*`; успешного native lifecycle-прогона или подтверждённого чтения AGENTS/CLAUDE/GEMINI реальными клиентами пока нет. Детерминированно проверены обработчики hooks, форматы конфигурации и операции ядра. Эти уровни проверки показываются отдельно.

Для полного native приёмочного прогона остаётся использовать среду клиента с разрешёнными проектными инструментами, выдать одну свободную задачу, получить наблюдаемые lifecycle события, передать фактический отзыв и продолжить в новом чате. Пока это ограничение подтверждения интеграции, а не скрытая отметка «всё автоматически работает».


## Исправление запуска Windows hooks — 2026-10-02

Скриншоты пользователя показали ошибки всех запусков с `hook exited with code 1`. Первое исправление добавило оператор `&` и прошло ручную проверку через PowerShell, но не устранило сбой клиента: это была проверка другой оболочки. Механизм command hooks Codex использует `COMSPEC /C` (на Windows `cmd.exe`). PowerShell-команда с ведущим `&` в этой оболочке воспроизводимо завершается кодом 1.

Установщик теперь явно вызывает `powershell.exe -NoProfile -NonInteractive -EncodedCommand`: литеральные Unicode-пути и оператор вызова находятся внутри UTF-16LE-команды, а не в строке, разбираемой cmd. Сохраняется код завершения Python. Повторная установка удаляет прежние команды протокола, включая кодированные, и сохраняет сторонние хуки. Конфигурация этого проекта обновлена.

Проверки: 37 runtime тестов прошли, включая все шесть событий через `COMSPEC /C`, путь с кириллицей, пробелами, `$` и одинарной кавычкой, повторную установку и сохранение сторонних hooks. Все шесть команд рабочего проекта отдельно выполнены через cmd с кодом 0. Изолированный тест установленным Codex app-server подтвердил `hook/completed` со статусом `completed` для `SessionStart` и `UserPromptSubmit` и передачу контекста. Отчёт: `build/native-hook-launch-report.json`. Тест использовал отдельный CODEX_HOME, доверие только своим тестовым определениям и локальный недоступный mock provider; реальных вызовов модели не было. Это проверка запуска двух событий, а не полный рабочий цикл модели.

Реальные проектные hooks имеют изменённые определения и требуют повторного доверия пользователя в Codex. Глобальные разрешения и доверие пользователя агент не менял. До загрузки и подтверждения новых определений работа текущего чата не считается проверенной.
